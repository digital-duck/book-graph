book-graph

Concept books from concept graphs, on GraphLang

press > book > chapter · one engine, one web app, every book

wen.gong.research@gmail.com

https://github.com/digital-duck/book-graphv1 · early prototype
book-graph turns a concept graph per chapter into a published concept book: one section per concept in teaching order, an interactive navigator, a web site. It replaces a fork-per-book model with one engine and one web app, and runs on GraphLang recipes like app-graph, work-graph and data-graph.

Outline

    The outline lists every slide title; click a line to jump.

    A concept book, built from a graph

    • A chapter is a graph of what it teaches: primitives, the concepts built from them, and what they are for.
    • The book writes one section per concept, in an order where every idea comes after what it needs.
    • It ends with a payoff: the capstone, and how everything comes together in it.
    • Readers explore it through an interactive navigator, at their level and in their language.
    The tutorial's chapter: distance and time are primitives (brown), speed, velocity and acceleration concepts (green), braking distance the application (red), the capstone the chapter's book is written toward. The colours are the navigator's.

    The problem: one forked repo per book

    • Each cb-* book forked the whole app: frontend, FastAPI backend, SPL workflow, scripts.
    • A book is really graph.yaml + settings + generated pages; the rest is copied boilerplate.
    • The copies drift. A fix must be ported by hand to every repo.
    • Publishing is per-repo glue: sync scripts, .env, deploy scripts.

    Measured across the repos

    13 cb repos (cb-zinets aside), 260 chapter graphs
    6 different copies of the navigator generator concept_graph.py
    cb-calculus, cb-linalg, cb-chemistry, cb_biology run an older frontend (≈700 lines apart)
    generation: a 400-line SPL file shelled out from the API
    The plan's diagnosis, confirmed while building: the navigator script exists in six versions, and most cb repos are on an older frontend than the template. A shared engine removes the drift by construction.

    The idea: a book is data, not a repo

    • press > book > chapter: a library of books, each a book.yaml and a graph per chapter.
    • The engine, the recipes and the web app are installed once; a fix reaches every book by upgrading one package.
    • Two ways in: a graph authored by an expert or a teacher, or one extracted from a textbook.
    • One way out: pages, navigator, site, catalog, all generated, all reproducible.
    ~/book-graph/library/
  catalog.json
  acme/physics/book.yaml
  acme/physics/chapters/ch01/

    The concept graph

    primitives:
  distance: {defines: How far something travels.}
  time:     {defines: How long something takes.}
concepts:
  speed:
    composed_of: [distance, time]
    defines: Distance travelled per unit of time.
applications:
  braking_distance:
    needs: [acceleration, speed]
    defines: How far a car travels while braking.
    • The ConceptBook format: every existing graph loads unchanged (260 / 260).
    • labels: {zh: …} per language, diagram: hints, tier.
    • bgr validate: acyclic, declared, reducible to primitives, defined, no duplicate ids, capstone is a node.
    $ bgr validate acme/physics
ok   ch01
    Checks were chosen by measuring each candidate on the 260 real graphs: the capstone check found three real broken chapters in cb-world-powers; connectivity and orphan checks were dropped as noise.

    Teaching order

    • Every node after its prerequisites, and early the nodes that unlock the most others.
    • Computed by zinet, shared with GraphLang, app-graph and work-graph; no private copy.
    • Restricted to what the capstone needs.
    • Identical to the old apps' order on all 260 graphs.
    $ bgr order …/ch01/graph.yaml
distance
time
speed
velocity
acceleration
braking_distance
    Deterministic too: the heap breaks ties by node id, so every recipe step, in its own subprocess, computes the same order.

    Generation is a GraphLang recipe

    generate_chapter

    SOLVE prepare: validate, plan, style guide
    GUARD may it write here (Cedar)
    LOOP per section, in teaching order:
    cache → GENERATE write → primitive-budget check → GENERATE refine once → cache + page
    GENERATE payoff for the capstone
    SOLVE book page: contents + payoff
    • Replaces the 400-line SPL workflow; the prompts are verbatim.
    • Deterministic steps are plain Python, JSON in, JSON out.
    • Every step that writes is risky: true, reachable only through the GUARD.
    • Transient model failures retried in the recipe.
    $ bgr generate acme/physics
ok   ch01 core.en sonnet (7 model calls) …/book_braking_distance.html
    Six sections plus the payoff. Levels map to style profiles (intro is Feynman-style, research keeps proof rigor for math, physics and engineering). Every level, language and model combination is a variant.

    Every section is cached, old ones reused

    • Keyed by what reaches the prompt: language, style, full model, label, definition, and a hash of the prompts.
    • A second run costs 0 model calls; editing one definition regenerates one section.
    • Legacy cache: the SPL apps' spl3 store, read with spl3's own keys.
    • Cross-chapter recaps: a concept an earlier chapter introduced is recapped, not re-derived (press's rule, byte for byte).

    Measured on cb-meta-health

    444 / 444 spl3 keys recomputed
    a migrated chapter, 11 concepts repeated from earlier chapters: 24 sections, 0 model calls
    “never regenerate existing content during migration”: met
    The legacy lookup keeps the plain context, because the SPL apps wrote their sections without the recap note; the note still shapes new sections.

    Runs that resume

    • Every generate is a run with a ledger: each chapter × level × language × model, its status and calls.
    • --resume last runs only what is not done.
    • Inside a chapter the section cache is the resume: a re-run after failing at 3 of 6 calls costs 3.
    • --budget caps the whole run; it stops after two failures in a row; Ctrl-C saves it.
    $ bgr generate acme/physics --budget 500
…
^C
interrupted: run …-4867 saved; continue with:
  bgr generate acme/physics --resume …-4867
$ bgr runs acme/physics
20261125-…-4867  done   4/4 done  15 calls
    GraphLang's checkpoints were not enough here: a LOOP is one checkpoint step, so a failure inside the section loop would re-run the whole loop. The cache already skips finished rounds, so the resumable unit is the book run.

    Two paths into a book

    • B: source: {pdf: chemistry-2e.pdf, chapter: 3} in book.yaml. A: the chapter's own graph.yaml.
    Both paths meet at validation. Build waits for every chapter's generation; publish waits for the build.

    Path B: ingest and extract

    • ingest: concept-book-press's PDF ingester; one chunk per section from the PDF's bookmarks.
    • extract: a recipe with press's two model passes (the concepts, then their prerequisites).
    • Then a deterministic cleanup: dependency-less concepts become primitives, unknown dependencies dropped, labels kept, tiers from the edges.
    • Validated; one repair call if it fails; still invalid → graph.draft.yaml.

    Checked against press's own output

    55 chapters from its two PDFs: same chunks, whitespace aside
    190 / 190 of its extracted graphs pass the cleanup and validation
    2 bugs fixed in press's YAML repair: a bare colon got through, and valid YAML got broken (31 of 190)
    press's prompts said "a physics textbook" for every book; the subject is now a parameter. A live-model extraction has not been run yet: the next thing to try, on one chapter.

    The pipeline: a manifest per step

    • Every step writes STEP.out.yaml: proof it ran, OK or NOT_OK.
    • It fingerprints its inputs: an edited graph makes validation stale, and blocks what follows.
    • bgr next starts every ready step in the background, then exits. Cron, or --watch.
    • No step starts another; there is no run command.
    # pipeline/ch01/3-validate.out.yaml
step: 3-validate
chapter: ch01
status: OK
inputs:
  graph: d4274f831666db91
  capstone: braking_distance
summary: 6 nodes, valid
review:
  status: approved
  by: editor
  note: graph checked
    Ready means: the step before it is OK, approved and still current; and its own manifest is missing, stale, rejected or marked for retry. A NOT_OK step reruns once its input is fixed or it is retried; a failed generation resumes its run.

    Human review at every step

    $ bgr status acme/physics
       ch01  3-validate  OK, review approved   done              6 nodes, valid
       ch01  4-generate  OK, review approved   done              run …: done (1 done)
       book  5-build     OK, review pending    awaiting review   built …/dist
       book  6-publish   -                     5-build not approved (or stale)
$ bgr approve acme/physics 5-build -m "site previewed"
5-build: approved
$ bgr next acme/physics
started 6-publish (log: …/pipeline/logs/6-publish.log)
    • approve lets the next step start; reject -m NOTE runs it again; retry reruns a NOT_OK one.
    • Approving 5-build is publish's confirmation: async mode has no terminal to ask in.
    • pipeline: {auto_approve: [...]} lets chosen steps through.
    Verified on a migrated cb-meta-health: nine validations ran as background processes, two at a time, in seven seconds; approve -c all released generation for every chapter.

    One web app for every book

    • concept-book-base's frontend, shipped inside the package.
    • Per-book values come from site:: title, tagline, tags, logo, base path, models.
    • bgr build: export the book, write the config, run Vite; about 2 s once the packages are cached.
    • The navigator is concept-book-base's page, ported byte for byte (260 / 260).

    Checked in Chromium

    cb-meta-health: the same rendering as its own build (home, 9 cards, navigator, contents, content panel)
    cb-calculus, cb-world-powers, cb_biology on the current app: no console errors
    the only difference: the model list shows the book's models
    Most cb repos run an older frontend, so a byte-identical rebuild of their sites would need their old code back. The gate used instead: the canonical app, built from the library, serves each book's content correctly.

    serve: the site with its local API

    • Generate, Export PDF and Settings work: the old FastAPI's API, kept, on the standard library.
    • Content is read live from the library: a page generated from the browser appears at once.
    • Generation runs the recipe in-process, streamed to the browser as events.

    Safety, kept and tightened

    ✔ 127.0.0.1 only
    ✔ API keys in memory; never echoed; never reach a recipe step
    ✔ new: Host must be this server (DNS rebinding)
    ✔ new: /api same-origin only: an <img> on another site could start a paid generation
    CORS stops another site from reading a response, not from sending the request; a GET that spends model calls needed an origin check. Verified in Chromium: generate from the content panel, then export a PDF.

    publish: a policy-checked deploy

    • The built site becomes one fresh commit on gh-pages, as gh-pages --no-history did.
    • A Cedar policy permits the push only when four facts hold.
    • git sees only HOME and SSH_AUTH_SOCK; it never waits for a password.

    publish.cedar

    site_ok a built site
    remote_ok GitHub or local, reachable
    branch_ok not the default, nor main/master
    base_ok built for where it is served
    $ bgr publish digital-duck/meta-health --dry-run
dry run: would push 917 file(s) … to git@github.com:digital-duck/cb-meta-health.git gh-pages
    The base path is read from the built page itself, so a folder built for another path cannot be published by mistake. Refused against the real remote for branch main and for a wrong base; nothing was pushed during development.

    Migrate the existing books

    • bgr migrate REPO: a cb repo into the library; old ids kept, so URLs do not change.
    • bgr export: a book back out, as an app's public/domains/.
    • Round trip on all 13 repos: file for file identical.

    Safety by design

    Recipes

    every step that writes is risky: true, behind a Cedar GUARD
    writes only under home, /tmp or declared roots
    steps run with PATH only: no keys, no home

    Content

    model output is untrusted: escaped; one exact figure shape allowed
    every path segment checked
    nothing overwritten without --force; a damaged catalog never overwritten
    These rules hold across generate, extract, build, serve and publish, and are written down in the repository's CLAUDE.md so later changes keep them.

    Demo

    # path A: an authored graph
bgr new acme physics --title "Everyday Physics"
# write chapters/ch01/graph.yaml, set capstone and models in book.yaml
bgr validate acme/physics && bgr order …/ch01/graph.yaml
bgr generate acme/physics
bgr serve acme/physics                         # http://127.0.0.1:8200/physics/

# the pipeline, a review at every step
bgr status acme/physics
bgr next acme/physics
bgr approve acme/physics 3-validate -c ch01 -m "graph checked"
bgr next acme/physics --watch 60

# path B, and the existing books
bgr ingest acme/chem --pdf chemistry-2e.pdf --chapter 3
bgr extract acme/chem -c ch03
bgr migrate ~/projects/digital-duck/cb-meta-health
    The same sequence as docs/GUIDE/Tutorial.md, which shows the real output of each command.
